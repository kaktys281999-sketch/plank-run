> Research report (English). Generated by a research agent on 2026-10-19; the decision-driving claims are fact-checked separately.

# Beatmap & audio-sync track: auto-charts from music for a body-controlled plank rhythm game

*Research date 2026-10-19. Many primary sites (huggingface.co, arxiv.org, web.dev, essentia.upf.edu, itch.io) were unreachable from the sandbox, so some facts come from search-result summaries and are marked as such. I ran my own benchmarks on synthetic tracks; scripts are in `/tmp/claude-0/-home-user/729fc64a-e018-57b6-953f-fd5b4106fb68/scratchpad/scripts/`.*

## 1. Key architectural decision
- **Analysis**: what the song *is*. It is expensive, the same for everyone, and cacheable by fingerprint.
- **Chart**: what the player *does*. It depends on level, session length and seed, and is cheap.

Store the analysis on the server and generate charts on the client from it, deterministically, with `generatorVersion+level+seed`. This gives:
- instant re-generation when the user's level changes;
- identical charts for leaderboards;
- the ability to fix generator bugs without re-analysing audio.

## 3. My benchmarks (synthetic pop tracks, known ground truth; Node/Python on a 4-vCPU server)
| Track | essentia multifeature | essentia degara | music-tempo | librosa beat_track |
|---|---|---|---|---|
| 124 BPM, 173 s | F=0.99, 14.6 s | F=0.99, 2.2 s | F=1.0, 3.6 s | F=1.0 |
| 96 BPM swing, 222 s | F=1.0, 19.2 s | F=1.0, 3.1 s | F=1.0, 2.9 s | F=0.95, 3.5 s |
| 140 BPM, 153 s | F=0.99, 13.6 s | F=0.99, 2.4 s | F=1.0, 3.0 s | **69.8 BPM (octave error)**, F=0.63 |

Takeaways:
- Synthetic audio is easy, so real music will score lower. Neural trackers lead on real data.
- Client analysis takes **3–20 s per song on a server core**. Phones are likely 2–5× slower (estimate), so run it in a Worker, show progress, and crop first.
- **A naive downbeat guess (every 4th beat, phase chosen by onset energy) scored F=0.** Kicks on beats 1 and 3 fool it, so a real downbeat model is needed.
- An energy + onset-density window picker found a chorus in 3 of 3 tracks (29.6 s, 30 s and 27.4 s of chorus inside a 30 s window).

## 4. Recommended pipeline
```
Client: file → decode (crop, mono 22.05 kHz for analysis) → fingerprint
  ├─ GET /analysis?fp=… → hit: generate chart locally, play
  └─ miss: (a) local quick analysis in a Worker → play now ("beta chart")
           (b) opt-in upload (or log-mel features) → server job queue
Server worker: ffmpeg → fpcalc/Chromaprint → Beat This! (beats/downbeats)
  → structure (allin1 or energy/novelty) → per-beat strength, RMS curve
  → best windows {30,60,120 s} → AnalysisJSON v1 → delete audio
```
- **Fingerprint**:
  - Chromaprint (LGPL; run as a separate `fpcalc` process server-side). In the browser use `rusty-chromaprint-wasm` (MIT).
  - Add a hash of the decoded PCM for an exact fast path.
  - Optional AcoustID: free only for non-commercial use. Paid tiers (per a search summary) are €50/mo for 1M lookups, €100 for 15M and €500 for 150M. It returns a MusicBrainz ID, which is a stable cache key and also gives title/artist.
- **Privacy/copyright**: keep audio on the device (OPFS/IndexedDB). The server keeps only analysis facts. An alternative is to upload Beat This!'s 128-bin log-mel input instead of audio, about 3 MB fp16 for 4 min. That is the same size but not playable audio; it requires reproducing the exact front-end.
- **AnalysisJSON**: `{schema, fp, models{beats,structure,versions}, bpm, beats[], downbeats[], beatStrength[], energy{hop,values}, sections[{start,end,label,energy}], bestWindows{30:[…],60:[…],120:[…]}}`.
- **Later**: move Beat This! small into the browser (onnxruntime-web; WebGPU in Chrome and in Safari 26 per secondary sources). Do not run it at the same time as MediaPipe during play; analyse before the session.

### Segment selection
- Prefer windows labelled `chorus`. Otherwise use the highest mean of (z-scored RMS + 0.5·onset density).
- Snap to downbeats and 4/8-bar phrases. Add a 1–2 bar fade-in/out.
- Session length by level: about 30–45 / 60–90 / 90–180 s.
- Interval mode: chorus = work, verse/bridge = "rest/knees" (HIIT style). Use section energy to modulate density.

## 5. Chart generation
The ML generators are trained on human finger/arm charts:
- DDC: CNN-LSTM placement + LSTM selection.
- TaikoNation: patterning.
- TCP (AIIDE 2025): NN onsets + beat snapping + pattern matching.
- Mapperatorinator: 219M-param Whisper-style model, CUDA.
- Beat Sage: two networks, timing then block type.

Their patterns ignore plank biomechanics and need GPUs. **Reuse DDC's split**: *placement* (when) comes from beats + onset strength, and *selection* (where) comes from a constraint-based rule engine. Then run a **linter**, the same idea as Beat Saber's parity checkers.

### Note types for planks
- **gem**: be in the zone at time t.
- **hold**: stay in the lane for d seconds. This is the isometric core and is scored as the fraction of time inside the zone.
- **slide**: a guided move from x1 to x2 over 1–2 beats.
- **rest/breath**: an empty bar used for voice cues.

Later options: a vertical axis (front camera: shift up/down) and "walls" to dodge.

### Algorithm sketch
1. Choose a move grid in beats so that the move interval lands in the level's band. This is independent of BPM and so robust to octave errors: at 170 BPM, move every 2 bars; at 70 BPM, every bar.
2. On each move slot, move with probability 0.35 + 0.6·energy, subject to:
   - max jump;
   - a movement budget over 10 s;
   - left/right time balance, so muscles are loaded evenly (mirroring).
3. Turn moves larger than 0.5 lane units into slides.
4. Between moves, place holds on downbeats (more in low-energy sections) or gems on beats where strength > 0.55 − 0.3·energy. Add half-beat gems only for Advanced. Cap density in notes/s, not notes/beat.
5. Warm-up: the first 2–3 s contain centre notes only. The last 10% are calmer.
6. **Linter**: for *every* consecutive pair of notes, require free time ≥ |Δx|/v_max + settle. Drop gems, never move targets.

My prototype first counted only "move events" and still produced a 0.21 s jump (a gem at the old lane just before a move). After the linter, the minimum free travel time was 0.64 s.

### Proposed parameters (validated on 45–90 s segments)
| | Beginner | Medium | Advanced |
|---|---|---|---|
| Min interval between moves | ≥3 s (every 2nd bar) | ≥1.6 s (bar) | ≥1.0 s (half bar) |
| Positions | 3 | 5 | 5 (+ vertical later) |
| Max jump / v_max / settle | 0.6 u / 0.67 u/s / 0.4 s | 0.7 / 0.8 / 0.3 | 1.2 / 1.33 / 0.25 |
| Move budget per 10 s | 1.2 u | 2.4 u | 4.0 u |
| Preview (approach) time | 3.0 s | 2.5 s | 2.0 s |
| Timing window (full / perfect) | ±350 / ±200 ms | ±250 / ±130 | ±180 / ±90 |
| Zone half-width | 0.25 | 0.20 | 0.15 |
| Prototype output | ~9 moves/min, 53–84 notes/min, 5–19 s holds | 20–31 moves/min, 54–77 notes/min | 20–35 moves/min, 71–95 notes/min |

For comparison:
- osu! at OD5 has a ±50 ms "300" window and a ±150 ms "50" window. Its AR5 preview is 1.2 s.
- StepMania's windows are Great ±90 ms and Boo ±180 ms (forum-sourced).

Our windows are wider because the input is a slow body moving into a *state*, and the visual feedback lags 100–250 ms. Tune with play-tests.

Adaptive difficulty:
- Ask the user's level at onboarding, then adjust between segments: hit rate above 90% → +1 step; form breaks → insert rest bars.
- Supernatural similarly calibrates to the user's body and adjusts difficulty dynamically.
- Seed the chart from the fingerprint, so charts are reproducible.

## 6. Sync, latency and calibration

### One master clock: `AudioContext.currentTime`
- Play the session segment as an **AudioBufferSourceNode** started at a scheduled ctx time. The start is sample-accurate. A 60 s stereo segment at 48 kHz is about 23 MB.
- Do not use `<audio>.currentTime` as the clock. Firefox rounds it to 2 ms, and to 100 ms with resistFingerprinting.
- Schedule sound effects with the lookahead pattern ("A tale of two clocks").
- songTime(perfNow) = ctxTime(perfNow) − startCtx − outputLatency − userOffset.
- Map performance time to context time with `getOutputTimestamp()`. It has had Safari bugs, so smooth it and sanity-check it.

### Platform latency APIs
- `outputLatency`: Chrome 102, Firefox 70, Safari 18.4.
- `baseLatency`: Safari 14.1+.
- Treat both as hints. The spec allows coarsening the value for privacy. On iOS, the value reported for Bluetooth was much smaller than the real latency. AirPods measured about 215–220 ms at connect and drifted to about 155 ms. SBC is roughly 170–250 ms.
- **You must calibrate per output route.** Re-prompt calibration on `devicechange` or when outputLatency jumps.

### Judge in camera-capture time
- Timestamp each pose sample with rVFC `metadata.captureTime` where it exists (WebRTC-type sources), else `expectedDisplayTime`/now minus a calibrated constant.
- Keep a short history of position over time, and judge each note against p(τ) for τ in [T−W, T+W]. This removes inference and smoothing latency from fairness.
- Render the circle extrapolated by about 50–100 ms (clamped) so it feels responsive, but never judge on the prediction.
- Treat dropouts shorter than 150 ms inside holds as "still in".

### Hands-free calibration ("nod to the beat")
- At onboarding, the user nods or shifts on 16 metronome clicks while the face detector runs.
- median(movement onset − click time), with MAD outlier rejection, gives audio output latency + capture latency + the user's own anticipation of the beat. That sum is exactly the offset needed for judging.
- Also offer a manual slider in 5–25 ms steps (Rhythm Quest moved to 25 ms steps in its 2025 rework; Clone Hero advises not to trust reported hardware latency).
- Offer a separate visual-offset slider (Rhythm Doctor style).
- Store the result per device and output route, and log it with session telemetry.

## 7. iOS Safari specifics
- Create and resume the AudioContext in the "Start" tap. Prime speech synthesis in the same tap (the prototype already does).
- Set `navigator.audioSession.type='playback'` (Safari 16.4+) so the silent switch does not mute Web Audio (per WebKit bugs 237322 and 251532). Keep the unmute.js or silent-`<audio>` hack only as a fallback.
- **Call getUserMedia with `{video:true, audio:false}` only.** Requesting the microphone ducks Web Audio volume and moves AirPods to HFP mono.
- On `visibilitychange`, auto-pause. Call `suspend()` then `resume()` when the context is "interrupted". The camera also stops in the background.
- Decode memory: decodes run serially. Crop and downmix first; a full 4-min stereo float track is about 90 MB, and iOS kills tabs that use too much memory.
- Screen Wake Lock works; it was broken in Home-Screen PWAs until iOS 18.4.
- Duck the music gain during voice cues.

## 8. Pitfalls checklist
- AGPL (essentia.js) and NC licenses (madmom models, MuQ, demucs weights) in dependencies.
- Octave errors. Bound gem density in seconds, and fold BPM to 70–160 for display.
- Tempo changes, rubato and songs with no clear beat. Detect this through tracker confidence or beat-interval variance, then fall back to an energy-only "flow" mode or warn the user.
- Non-4/4 meters. allin1 and Beat This! give downbeats; otherwise assume 4.
- Leading silence or encoder padding: MP3 decoder delay can shift the timeline by about 25–50 ms. Analyse the same decoded PCM you play.
- Re-encoded uploads change exact hashes. Use a perceptual fingerprint, plus a duration check.
- Bluetooth drift during a session. Allow a quick re-sync (a nod gesture) mid-pause.
- Charts that exceed body speed. Always run the linter, and play-test with the synthetic-render rig.

## 9. Data-model hint
Chart JSON: `{schema:"chart/1", analysisFp, generator:"rules-x.y.z", seed, level, segment{start,end,fadeIn,fadeOut}, notes[{t,k:"gem|hold|slide|rest",x,x2?,d?}]}`. Version everything, so old scores stay comparable.

## Recommendation

Split the work into two parts. (1) A per-song **analysis** that is expensive, runs once per song, and is cached for every user under an audio-fingerprint key: beats, downbeats, a per-beat strength/energy curve, sections, and the best 30/60/120 s windows. (2) A per-user **chart** that is cheap and deterministic: rules plus a constraint linter, run on the client from the analysis JSON with (generatorVersion, level, seed). Server: a Python worker with Beat This! (MIT code and weights, no madmom DBN). Song structure comes from all-in-one/allin1 (MIT), or from an energy/novelty segmenter if a legal review of its madmom and demucs dependencies does not pass. Results are keyed by Chromaprint, or by AcoustID/MusicBrainz ID on a paid plan, and the uploaded audio is deleted right after analysis. Client fallback for instant play and offline: an MIT-licensed JS tracker (music-tempo, or a custom spectral-flux + DP tracker) in a Worker, upgraded to Beat This! small via onnxruntime-web later. Do not use essentia.js (AGPL, plus models licensed for non-commercial use only) or madmom models (CC BY-NC-SA) in a closed commercial app. Chart rules: big moves only on bar or half-bar slots, with at least 3 s / 1.6 s / 1 s between moves for beginner / medium / advanced. A reachability linter checks every pair of consecutive notes. Holds (staying in a lane) are the main isometric note type. Notes are previewed 2–3 s ahead. Judging is spatial (is the circle inside the zone during ±180–350 ms) and runs in camera-capture time, not render time. Sync uses one clock (AudioContext) and plays the session segment as an AudioBufferSourceNode. Calibration is a hands-free "nod to the beat" test that measures audio output latency plus camera latency per output device (Bluetooth adds 150–300 ms that drifts). On iOS: set navigator.audioSession.type='playback', never request the microphone, resume the audio context after interruptions, and crop and downmix audio before decoding.

## Open questions

- Beat This! small model CPU and WASM/WebGPU inference time on a mid-range Android phone and iPhone. I could not measure it because huggingface.co and the JKU checkpoint host were blocked; it needs an on-device benchmark before deciding client vs server.
- Is rVFC metadata.captureTime exposed for local getUserMedia video in Chrome Android and iOS Safari, or must camera capture latency be a calibrated constant?
- Legal review of allin1's runtime dependencies: madmom DBN (BSD code; the third-party patent claim is unverified) and demucs weights (license disputed). If either fails, use Beat This! plus an in-house energy/novelty segmenter.
- Target region and music source: user uploads only, or also a licensed or royalty-free catalog? This decides whether AcoustID/MusicBrainz keys are worth paying for and how much offline human QA of charts is possible.
- Game geometry: 1D lanes (left/right shift) only, or 2D (adding up/down shift from the front-camera face position)? This changes the chart schema and the linter's v_max per axis.
- Should headphones be recommended or required? Speaker playback has lower and more stable latency, while Bluetooth needs per-route calibration and drifts over time.
- Real-music accuracy of the MIT JS trackers (music-tempo, audiojs/beat) versus Beat This! on a small annotated test set, for example the osu2mir subset or Harmonix annotations with your own audio. My benchmark used only synthetic tracks.
