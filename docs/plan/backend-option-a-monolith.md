# Вариант A. Переносимый модульный монолит: TypeScript + PostgreSQL

*Архитектурное предложение от 19.10.2026. Опирается на `docs/research/*.md` с поправками из `verify-backend-compliance.md`. Пометка (н/п) означает, что факт в этой сессии не проверялся. Цены хостингов в 2026 году нестабильны: Hetzner поднимал их 01.04 и 15.06, линейки CPX и CCX подорожали на 113–176%. Поэтому стоимость везде дана диапазоном.*

## 0. Тезис

Весь бэкенд — один Docker-образ на Node 24 LTS: Hono, Drizzle, Better Auth, pg-boss. Состояние хранится в одном месте, PostgreSQL. Файлы лежат в любом S3-совместимом хранилище. Образ одинаково запускается на VPS за €6, в Yandex Cloud, на Railway или Fly. Регион пока не выбран, поэтому главное свойство архитектуры — переносимость: ячейка `ru` отличается от ячейки `global` только файлом `.env`.

Почему этот вариант сильнее альтернатив именно для Plank Run:

1. **Россия отсекает почти все готовые платформы.** Запись ПДн россиян разрешена только в базу в РФ, причём это касается и иностранного SaaS, который получает данные прямо из браузера. Cloudflare в РФ режут, иностранный вход запрещён. Supabase Cloud, Firebase, Convex и Workers в RU-ячейку не поставишь. Self-hosted Supabase — это около десятка контейнеров. Наш вариант — один контейнер плюс Postgres у любого российского облака.
2. **Античит без второй кодовой базы.** Детерминированная симуляция `game-core` на TS работает и в браузере, и на сервере, ничего не нужно портировать. Пересимуляция минуты реплея занимает миллисекунды в том же процессе.
3. **Local-first снимает требования к доступности.** Игра целиком работает без сети, и это обязательно: в режиме «белых списков» недоступен любой наш сервер, даже российский. Сервер отвечает за синхронизацию, друзей, рейтинги и каталог. Час простоя — не инцидент, поэтому на Ф0–1 хватает одного узла.
4. **Всё в Postgres:** очереди, cron, сессии, rate-limit и лидерборды. Бэкапить, мониторить и переносить нужно один объект.
5. **Удобно для ИИ-ассистента.** Популярный стек со сквозной типизацией от zod-схемы до SQL. Миграции — обычный SQL в git, API описан в OpenAPI.

Честные слабости (подробнее в §18):
- эксплуатация лежит на вас: патчи, TLS, бэкапы, учения по восстановлению;
- в первые 1–2 недели этот вариант медленнее Supabase: нет готовых Auth UI, Storage и Studio;
- нет встроенного realtime;
- Better Auth с 07.07.2026 принадлежит Vercel, это риск управления проектом;
- на Ф0–1 единственный узел — точка отказа.

## 1. Принципы

- Источник правды для игрового процесса — устройство. Сервер делает то, чего нельзя сделать локально: несколько устройств, друзья, рейтинги, проверка, каталог.
- **Аккаунт не обязателен.** Гость получает всю игру и весь прогресс, вход нужен только для социальных функций. Это ещё и законный способ уйти от ч. 10 ст. 8 149-ФЗ: норма касается только ресурсов с авторизацией.
- Один образ. Роль процесса задаёт `ROLE=api|worker|all`, ячейку — `CELL=ru|global|…`.
- Каждый модуль владеет своей схемой Postgres. Модули обращаются друг к другу только через `service.ts`, это проверяет `dependency-cruiser` в CI.
- Внешние сервисы подключаются через адаптеры: `BlobStore`, `Mailer`, `SmsSender`, `JobQueue`, `PushSender`. Если у сервиса нет замены, он остаётся за интерфейсом.

- **Где ставить Ф0.** Если друзья в РФ, первая ячейка — российский VPS, а уведомление в РКН подаётся до открытия регистрации. Иначе — VPS в ЕС: это допустимо и для Узбекистана, потому что ЗРУ-1125 от 26.03.2026 требует локализации только для биометрии, генетики и абонентов связи. Казахстанскую ячейку заранее не строим: тамошний режим, похоже, ослабляется.
- **Нагрузка ничтожная.** 800k сессий в месяц — это ≈0,3 RPS в среднем и ×20 в пик. Два узла на Ф2 нужны ради отказоустойчивости, а не производительности.
- **Объём БД:** строка сессии с индексами весит ≈400 Б, на Ф2 набегает ≈0,4 ГБ в месяц. Реплеи (2–3 КБ) лежат в S3 с TTL 90 дней.
- **Дорогая часть — музыка.** На Ф2 первые загрузки треков дают ≈1,5 ТБ в месяц. В R2 исходящий трафик бесплатный, в РФ за него платим CDN. Снижаем объём так: AAC 128 кбит/с, отрезки по 45–90 с вместо целых песен, immutable-кэш в Service Worker.
- **Ячейки.** Пользователь выбирает страну проживания при регистрации, IP не учитываем. По стране клиент берёт адрес API из `cells.json`. Друзья и доски живут внутри ячейки. Связи между ячейками появятся позже через global directory, где хранится только handle→cell. Для ru это трансграничная передача: нужно отдельное согласие и уведомление в РКН.
- **Для сравнения:** у Supabase минимальная продакшен-конфигурация с PITR (Pro + Small + PITR) стоит ≈$130 в месяц на проект.

## 4. Модель данных

### 4.1 Идентификаторы
- Все первичные ключи — `uuid` v7. Их генерирует приложение, поэтому от версии Postgres мы не зависим. Id сессий, устройств и операций outbox генерирует **клиент**, и благодаря этому загрузка идемпотентна.
- Внутри UUID ячейка не кодируется. Во внешних ссылках (инвайты, вызовы, QR) она стоит префиксом: `ru-7KQ2M9XA`.
- Наружу `user_id` не показываем: в рейтингах видны только handle (уникален в пределах ячейки) и скин.
- Время хранится в `timestamptz`. Недели — ISO-недели в часовом поясе пользователя.

### 4.2 Только на устройстве, никогда на сервер
- Анкета PAR-Q целиком, включая ответы «да/нет»: травмы, давление, беременность. Туда же причина «осторожного маршрута», рост и вес, флаги боли после сессии.
- Кадры камеры, landmarks, детальные метрики техники.
- Калибровки камеры и аудиозадержки.
- Аудиофайлы пользователя и их названия.

Генератор плана (`packages/progression`) работает на устройстве. Сервер получает только **результат**: уровень, расписание, версию анкеты и факт «дисклеймер вер. N принят», без причин. Одно это решение снимает ст. 10 152-ФЗ (письменное согласие), ст. 9 GDPR и MHMDA.

## 5. API

- **Стиль.** REST + JSON под `/v1`, описание через `@hono/zod-openapi`. Схемы лежат в `packages/contracts` (zod 4), их импортируют и PWA, и сервер. Клиент — типизированный `hono/client`.
- **Валидация.** Входные объекты проверяются с `.strict()`: лишние поля дают 400, поэтому mass assignment невозможен. Лимит тела — 64 КБ на сессию и 512 КБ на батч. Ошибки возвращаются в формате RFC 9457 `problem+json`.
- **Версионирование.** Внутри `/v1` изменения только добавляются. Ломающие изменения уходят в `/v2`, а `/v1` живёт ещё не меньше 6 месяцев. `GET /v1/config` отдаёт `minClientVersion`; на запись от слишком старого клиента сервер отвечает 426. У реплея, AnalysisJSON и карты есть свой `format_ver`. CI сравнивает OpenAPI с прошлым релизом через oasdiff.

## 6. Аутентификация

- **Библиотека и сессии.** Better Auth 1.7 (MIT) с Drizzle-адаптером, серверные сессии в Postgres. Cookie `__Host-` с флагами HttpOnly, Secure, SameSite=Lax живёт 60 дней со скользящим продлением.
- **Один origin.** PWA и API отдаются с одного адреса: Caddy раздаёт статику и проксирует `/v1`. Поэтому нет CORS, а CSP `connect-src 'self'` закрывает утечки на сторонние домены.
- **CSRF.** SameSite, проверка `Origin` и приём только `application/json`.
- **Паролей нет вообще.**

| Способ | global / uz | ru | Примечание |
|---|---|---|---|
| Гость (вся игра) | да | **да, по умолчанию** | Данные только на устройстве |
| Яндекс ID | опционально | **да** | generic OAuth, есть хелпер |
| VK ID | — | **да** | OAuth 2.1, PKCE S256, `device_id` |
| Телефон, SMS-код | — | **да** | плагин `phoneNumber`, российский SMS-шлюз, только +7 |
| Email-код (OTP) | да | **выключен** | По ч. 10 ст. 8 149-ФЗ спорно, считаем зоной риска |
| Google / Apple / Telegram OIDC | да (Telegram популярен в UZ) | **нет** | ст. 13.55 КоАП (199-ФЗ, с 07.07.2026) касается **любого** иностранного IdP, Telegram тоже |
| Passkeys | Ф1 | Ф1 (после входа через VK, Яндекс или телефон) | WebAuthn, биометрию проверяет ОС |

- **Набор способов входа задаётся конфигом ячейки.** Применяется ли запрет к владельцу, который не резидент РФ, не подтверждено. Поэтому флаг `AUTH_FOREIGN_IDP` есть и у global-ячейки, а до запуска в РФ нужна консультация юриста.
- **Гость → аккаунт.** Анонимных пользователей на сервере не заводим, гость живёт только в Dexie. При входе клиент сливает свой outbox обычной синхронизацией:
  - сессии загружаются со своими id и без токенов попыток, поэтому получают статус `unranked`;
  - план и уровень — по правилу последней записи (LWW);
  - разблокировки объединяются.

  Логики слияния на сервере нет. Если воронка покажет, что людям нужен рейтинг до входа, подключим плагин `anonymous`. Его `onLinkAccount` одной транзакцией перенесёт строки анонима и удалит его.
- **Связывание аккаунтов.** Автоматическое — только когда email подтверждён и у провайдера, и у нас. Остальные связи пользователь создаёт явно, из настроек, будучи залогиненным. Иначе возможен захват аккаунта.
- **Лимиты.** SMS: 1 в минуту и 5 в сутки на номер, 20 в час на IP, капча (Yandex SmartCaptcha) после второй отправки. Это защита от SMS-pumping, на нём теряют деньги. Код вводится не больше 5 раз. Админам обязательны passkey или TOTP (плагин `twoFactor`).

## 7. Офлайн-синхронизация

**Клиент.** Любое изменение пишется локально и одновременно в `outbox`: `{op_id: uuidv7, type, entity_id, payload, schema, tries}`. Отправка идёт:
- при старте;
- на событие `online`;
- при возврате на вкладку (`visibilitychange`);
- после конца сессии.

Повторы — с экспоненциальной задержкой и джиттером. На Background Sync не рассчитываем: в Safari его нет. Очередь должна переживать дни без сети, ведь белые списки — это норма, а не авария.

**Протокол.** `POST /v1/sync` принимает до 50 операций. Каждая выполняется в своём savepoint, и на каждую сервер отвечает `applied`, `duplicate` или `rejected{code}`. На любой из трёх ответов клиент удаляет операцию; при 5xx или сетевой ошибке оставляет. Идемпотентность держится на естественных ключах или на `ops.sync_ops(user_id, op_id)`.

**Конфликты:**
- **Сессии неизменяемы:** `INSERT … ON CONFLICT (id) DO NOTHING`. Тот же id с другим `payload_hash` получает `rejected{conflict}` и пишется в журнал.
- **XP, gems и звёзды клиент не присылает.** Сервер выводит их из сессий через `ledger` с уникальным ключом. Клиент показывает оптимистичное значение, потом сервер его заменяет.
- **Разблокировки** — множество, которое только растёт; при слиянии объединяем.
- **Профиль** — LWW по каждому полю по `client_ts`. Метку зажимаем в окно `[received_at − 30 дней; received_at + 5 мин]`.
- **План** — LWW по `generated_at`. Смену уровня сервер обрезает до +1 за сессию и +3 за неделю: это правила безопасности из progression.md, и они защищают доски уровней.

**Pull.** `GET /v1/sync/changes?since=<seq>` отдаёт строки с `updated_seq > since`. Транзакция с меньшим seq может закоммититься позже. Поэтому сервер отдаёт данные только до «безопасного горизонта» (seq старше 2 с), а клиент запрашивает с перекрытием и убирает дубли по id.

**Время и рейтинг офлайн.**
- Клиент присылает `started_at` по часам устройства и `active_ms` по монотонному таймеру.
- Клиент заранее берёт до 5 токенов попыток на доску, каждый живёт 7 дней. Сессия с таким токеном проходит обычную проверку и попадает в рейтинг с пометкой «офлайн».
- Сессия без токена получает статус `unranked`, но идёт в историю и недельную цель.

## 8. Лидерборды и античит

**Конвейер.** `PUT /sessions/{id}` → статус `received` → задача pg-boss `verify-session`. Воркер проверяет:
1. **Токен попытки:** он существует, принадлежит этому пользователю, не истёк, не использован, относится к той же доске, и `started_at ≥ issued_at`.
2. **Границы из `levels.score_rules`:** не больше N очков в секунду, допустимая длительность, предел точности, `active_ms ≤ ended_at − started_at`, число сессий в час.
3. **Реплей:** контрольная сумма и строгий декодер.
4. **Пересимуляцию:** `game-core@sim_version` прогоняет реплей с тем же seed и картой. Счёт должен совпасть **точно**, очки целые.
5. **Статистику сигнала:** нулевой джиттер, нечеловеческая задержка реакции или периодичность дают статус `flagged`.

Если всё сошлось, сессия получает `verified`. Дальше upsert в `board_best` по `all` и по неделе (`WHERE excluded.score > board_best.score`), начисление в `ledger` и обновление `weekly`. Сессию со статусом `flagged` видят только сам игрок и модератор.

**Формат реплея.** Заголовок: `format_ver`, `sim_version`, seed, `board_id`, частота 30 Гц. На каждый тик — `int8 x`, `int8 y` и байт флагов (в кадре, техника ок, пауза). После дельта-кодирования, varint и `CompressionStream('deflate')` выходит ≈2–3 КБ в минуту. Это управляющий сигнал, а не landmarks. Ритм-игра позиционная, поэтому ноты судятся по тому же сигналу.

**Детерминизм.**
- Фиксированный шаг 1/30 с, в путях подсчёта очков только целые числа или fixed-point.
- PRNG по seed (sfc32). `Math.random` и `Date` в симуляции запрещены.
- Сервер держит несколько версий симуляции через npm-алиасы (`game-core-v3`, `game-core-v4`) и проверяет реплеи старых клиентов их версией.
- CI прогоняет golden-корпус реплеев на Node, Chromium и WebKit, счёт должен совпасть до очка.
- Минута реплея — 1800 тиков и единицы миллисекунд CPU. Весь объём Ф2 укладывается меньше чем в час CPU в месяц.

**Чтение.**
- Топ-N — индексный скан.
- Ранг считается как `count(*) WHERE score > $mine`; это приемлемо до ~10⁶ строк на доску.
- Доска друзей — JOIN с `friend_edges`.
- Топ-100 кэшируется в процессе на 30 с.
- Valkey ZSET подключаем только при p95 > 50 мс или досках больше миллиона строк. Это кэш, его всегда можно пересобрать из Postgres.

**Пределы.** Бот, который синтезирует правдоподобный сигнал, пересимуляцию пройдёт: веб не умеет аттестовать устройство. Поэтому:
- по умолчанию показываем доску друзей;
- публичная доска — только по согласию (в РФ это ещё и согласие на распространение ПДн);
- топ-10 проверяем вручную, при необходимости ставим теневой бан;
- у пользовательских песен есть только доски друзей.

## 9. Музыка и битмапы

**Курируемый каталог (40–80 треков).** Python в проде не нужен. Команда `pnpm music:ingest ./masters/*.wav` запускает контейнер `audio-worker` локально или на почасовой VM и делает:
1. нормализацию громкости ffmpeg loudnorm до −14 LUFS;
2. кодирование в AAC;
3. доли и сильные доли через Beat This! (MIT, без DBN из madmom);
4. энергию и онсеты через librosa;
5. секции (энергия и новизна; allin1 — только после юридической проверки его зависимостей);
6. сборку AnalysisJSON v1 и загрузку через `/v1/admin/tracks` вместе со снимком лицензии.

Ключи объектов — хеш содержимого (`audio/{sha256}.m4a`, `analysis/{sha256}/{algo}.json.gz`), заголовок `Cache-Control: immutable`. Когда треков станут сотни, тот же контейнер превратится в постоянный воркер на таблице с `SELECT … FOR UPDATE SKIP LOCKED`: у pg-boss нет Python-клиента.

**Лицензии.**
- `license_code` берётся из белого списка: CC0, CC-BY-4.0, royalty-free с разрешением на игры, прямой договор. Список закреплён CHECK-ограничением, поэтому NC, ND и SA в каталог не попадут физически.
- `proof_key` хранит снимок страницы лицензии на дату, `regions` — разрешённые регионы.
- Экран атрибуций собирается из таблицы.
- `takedown` скрывает трек, удаляет объект и архивирует доски.

**Свои треки пользователя.** Файл не покидает устройство.
- Клиент считает `file_sha256`. MP3, пересланные через мессенджер, у друзей побайтно совпадают, поэтому кэш заметно помогает.
- Затем запрос `GET /v1/analyses/file_sha256/{h}`. Промах → анализ в Worker трекером под MIT. Затем, если пользователь согласен, `POST /v1/analyses` отправляет только ритм-факты с пометкой `trust=client`.
- Позже добавим Chromaprint (WASM, MIT): он находит перекодированные копии того же трека.
- Удалять на сервере нечего. При удалении аккаунта в его анализах обнуляется `created_by`, и связь «человек ↔ песня» исчезает.

**Карты.** Клиент генерирует их детерминированно из анализа по `generator_version`, сложности, отрезку и seed. Сервер умеет повторить генерацию в `game-core` для проверки. В `music.charts` хранятся только ручные карты.

**Доставка.**
- global — R2 на своём поддомене;
- ru — Yandex Object Storage + CDN или Caddy ячейки;
- CORS разрешён только своему origin;
- Service Worker отвечает на Range-запросы, иначе Safari не играет аудио из кэша.

## 10. Realtime

До Ф2 realtime не нужен: социальность закрывают асинхронные вызовы, призраки и push.

Для дуэлей добавим WebSocket в тот же процесс (`@hono/node-ws`). Комната живёт в памяти: 2 игрока × 20 Гц мелких сообщений, так что один узел держит тысячи комнат. Сервер только ретранслирует сообщения, а вердикт выносит по реплеям обоих игроков через `verify-session`. При нескольких узлах Caddy липко маршрутизирует по `room_id`.

Если понадобятся presence, история или кластер, ставим Centrifugo с движком Valkey отдельным контейнером. Контракт для клиента при этом не меняется. WebRTC P2P не берём: TURN стоит денег и плохо переносит фильтрацию в РФ.

## 11. Push-напоминания

- **Отправка.** Web Push с VAPID-ключами отдельно на каждую ячейку. Библиотека `web-push` 3.6.7 (MPL-2.0, последний релиз в 01.2024) запинена; протокол простой, при необходимости заменяется своим кодом.
- **Отбор.** Cron pg-boss раз в 5 минут выбирает тех, у кого наступило локальное время напоминания: сегодня ещё не отправляли, недельная цель не выполнена, сейчас не тихие часы.
- **Очистка.** Ответ 404 или 410 удаляет подписку.
- **Содержимое.** В payload нет ПДн, только текст и id, потому что он идёт через push-сервисы Google, Apple и Mozilla. Тон без вины, ночных пушей нет.
- **Ограничения.** На iOS push работает только в установленной PWA. В РФ доставка через FCM ненадёжна (н/п).
- **Запасной вариант.** Экспорт **.ics** с повторяющимся напоминанием в календарь. Работает без push, без сервера и офлайн.

## 12. Админка и контент

**Контент как код.** Уровни, игры, скины и сезоны — JSON в `content/` в git. Их проверяет та же zod-схема, что и игра. CI-команда `content:publish` идемпотентно создаёт новые версии и сбрасывает ETag каталога. Одному человеку с ИИ-ассистентом это удобнее CMS: есть диффы, ревью и откат.

**Веб-админка** — ленивый маршрут `/admin` того же SPA. Она нужна только для того, что не живёт в git:
- треки и лицензии;
- очередь `flagged`-сессий и жалоб;
- поиск пользователя, бан и теневой бан;
- флаги;
- состояние очередей.

Каждое действие пишется в `audit_log`. Сырые данные смотрим в Drizzle Studio через SSH-туннель.

## 13. Наблюдаемость и бэкапы

- **Логи:** pino в JSON с `request_id` и хешем `user_id`. IP держим только в памяти rate-limit. Срок хранения — 14 дней.
- **Ошибки.**
  - global: Sentry с `beforeSend`, который вычищает PII, и `tunnel` через свой домен.
  - ru: **только GlitchTip внутри ячейки.** Иностранный SaaS, получающий данные прямо из браузера россиянина, — это первичный сбор ПДн за рубежом. По той же причине в RU-ячейке нет иностранных ESP, аналитики и шрифтовых CDN.
- **Метрики:** `/metrics` (prom-client) и `pg_stat_statements`. Отдельная страница в админке показывает p95, глубину очередей, долю `flagged` и возраст последнего бэкапа. Аптайм проверяет внешний пинг `/readyz`, алерты идут в Telegram владельцу.
- **Бэкапы.**
  - Ф0: каждую ночь `pg_dump -Fc`, шифрование age, загрузка в S3 *другого* провайдера *той же страны*. Для ru это обязательно, иначе получится хранение за рубежом. Хранение: 7 дневных, 4 недельных, 6 месячных копий.
  - Ф1 и дальше: PITR у managed-провайдера или WAL-G, RPO ≤ 5 мин.
- **Учения.** Раз в месяц GitHub Action поднимает Postgres, восстанавливает последний дамп, прогоняет миграции и проверочные запросы.
- **Бонус local-first.** История есть и на устройствах, поэтому после катастрофы клиенты сами идемпотентно дозагрузят сессии.

## 14. Безопасность: чек-лист

- [ ] TLS и HSTS через Caddy; один origin; CSP `default-src 'self'`, никаких сторонних скриптов.
- [ ] Cookie `__Host-` с HttpOnly, Secure, SameSite=Lax; проверка `Origin` на всех запросах записи.
- [ ] zod `.strict()` на каждом входе, лимиты тела, строгий декодер реплеев с фаззингом в CI.
- [ ] Rate-limit через `rate-limiter-flexible` с хранилищем в Postgres на SMS/OTP, sync, attempts и invites.
- [ ] Роли БД: `app` (DML без DDL), `migrator` (только в CI), `readonly`. Postgres недоступен снаружи.
- [ ] Секреты в sops+age, ключи VAPID и S3 отдельные для каждой ячейки, ротация раз в год.
- [ ] Контейнер не от root, файловая система только для чтения, Renovate + osv-scanner, SBOM.
- [ ] На VPS: только SSH-ключи, ufw, unattended-upgrades.
- [ ] Бакеты приватные; для реплеев и экспортов подписанные URL на 5 мин; публичен только `audio/`.
- [ ] Админка за passkey или TOTP, все действия в журнале; стоп-слова для ников, блокировки и жалобы.
- [ ] Чата нет: в РФ он грозит статусом ОРИ. Только реакции и вызовы.

## 15. Приватность

- **Минимизация.** На сервере хранятся только идентификатор входа (email, телефон или OAuth-id), handle, возрастная группа, уровень, итоги сессий и друзья. Что остаётся на устройстве, перечислено в §4.2.
- **Экспорт.** Задача собирает zip с JSON и реплеями. Подписанная ссылка живёт 24 ч, файл удаляется через 7 дней.
- **Удаление.**
  - Сразу: отзыв сессий и скрытие профиля.
  - В течение 30 дней: каскадное удаление строк и объектов по префиксу `replays/u/{user_id}/`, записей в досках и вызовах; обнуление `created_by` в анализах.
  - Из бэкапов данные уходят с ротацией копий, это прописано в политике.
  - Для Google Play есть публичная страница удаления.
- **Сроки хранения.** Реплеи — 90 дней, кроме рекордов и активных вызовов. Неактивный аккаунт удаляется через 24 месяца, с предупреждением.
- **Согласия.** Журнал согласий с версиями документов. Для ru — отдельное согласие на обработку и на публичный рейтинг, а уведомление в РКН подаётся **до** открытия входа.

## 16. Тесты и CI/CD

- **Монорепо** на pnpm: `apps/web`, `apps/server`, `packages/{contracts,game-core,progression}`, `content/`, `tools/audio-worker`.
- **Unit (Vitest):** правила начислений и границ; property-тесты (fast-check) для sync и ledger.
- **Интеграционные:** Testcontainers с настоящим Postgres 17, каждый тест в транзакции с откатом. БД не мокаем: `ON CONFLICT` и pg-boss проверяются только на живой базе.
- **Детерминизм:** golden-реплеи дают одинаковый счёт на Node и в браузерах (Playwright).
- **E2E:** Playwright с фейковой камерой (она уже есть в `test/`) против docker compose. Сценарий: «офлайн → сыграть → онлайн → сессия в доске».
- **Контракты и границы:** oasdiff и dependency-cruiser.
- **Миграции:** `drizzle-kit generate`, затем ревью SQL, затем `migrate` отдельным шагом перед выкаткой. Ломающие изменения — по схеме expand → backfill → contract.
- **CD (GitHub Actions):**
  1. сборка multi-arch образа (amd64 + arm64);
  2. push в GHCR и в реестр RU-ячейки (Yandex Container Registry);
  3. матрица по ячейкам с одним и тем же digest: `migrate` → `compose pull && up -d` → проверка `/readyz` → при ошибке откат на прошлый тег.

  С Ф1 — две реплики api и выкатка без простоя (поочерёдно или через Kamal 2). На Ф2 добавляется нагрузочный тест k6.

## 17. Миграции и путь выхода

| Сценарий | Как | Трудоёмкость |

| Цены и наличие у хостеров | средняя / низкий | переносимый образ, переезд за часы |
| Расхождение детерминизма | средняя / средний | целочисленная sim, golden-тесты, несколько версий sim |
| SMS-pumping и стоимость SMS | средняя / средний | лимиты, капча, только +7, VK/Яндекс в приоритете |
| Читеры в топе | высокая / низкий | доски друзей по умолчанию, пересимуляция, ручная проверка топа |
| Потеря данных в Safari (ITP) | средняя / средний | предложить вход после второй сессии, `persist()`, серверная копия |
| Бэкенд раньше продукта | высокая / средний | M1–M2 минимальны, остальное — по сигналам от друзей |

## 19. Что строить первым

1. **M0, без сервера (≈1 нед.).** Dexie, UUIDv7, outbox, `packages/contracts`, `game-core` с seed и записью реплея. Модели и WASM — с собственного origin, кэш с первого запуска.
2. **M1, ячейка для друзей (1–2 нед.).** Hono и схема v1 (auth, profiles, consents, devices, sessions). Вход по конфигу ячейки: ru — Яндекс/VK, global — email-OTP/Google. Затем `/v1/sync` и `/v1/me`, compose на VPS, ночной бэкап и учение восстановления, Sentry или GlitchTip.
3. **M2, друзья и проверка (1–2 нед.).** Инвайты, друзья, attempts, `verify-session` с пересимуляцией, доска друзей, призрак своего рекорда.
4. **M3, контент и права (1 нед.).** Каталог из `content/`, версии уровней, экспорт и удаление, журнал согласий, минимальная админка.
5. **M4, ритм (2 нед.).** Ingest-CLI, хранилище, атрибуции, кэш анализов, версии карт.
6. **M5, мета (1 нед.).** Ledger, звёзды, скины, недельная цель с заморозкой, push и .ics.
7. **M6, публичный запуск (1–2 нед.).** Managed PG с PITR, 2 реплики, rate-limit, k6, DPIA, уведомление в РКН, вход по телефону для ru, вторая ячейка по необходимости.
8. **Потом:** публичные доски по согласию, global directory, дуэли на WS, затем Centrifugo.

## 20. Итог

Вариант A первые две недели уступает Supabase в скорости, а на 100k MAU проигрывает Cloudflare в цене ($250–500 против $50–150). Но только он одинаково работает при любом выборе региона: тот же образ ставится в Yandex Cloud для РФ и на VPS за €6 для остального мира. Пересимуляция на сервере не требует второй кодовой базы, состояние хранится только в Postgres, а от любого провайдера можно уйти за часы. Регион не выбран, команда — один человек, законы меняются раз в полгода. В таких условиях это самый дешёвый способ не принимать необратимых решений.
