# Судья: масштаб, доступность, переносимость

*19.10.2026. Оцениваю `backend-option-a-monolith.md`, `backend-option-b-supabase.md` и `backend-option-c-local-first.md` с одной точки зрения. Критерии: рост до 100k MAU, работа под «белыми списками» и троттлингом CDN, готовность к RU- или UZ-ячейке, lock-in, будущие функции, корректность модели данных и синхронизации, безопасность миграций. При расхождениях приоритет у поправок из `verify-backend-compliance.md`. Требования к функциям взяты из `spec-product-progression.md` и `spec-rhythm-music.md`. Пометка (н/п) — не проверено.*

## 1. Итог

**Побеждает C (local-first) с оценкой 8,3 из 10.** У A — 7,3, у B — 5,9.

Серверный стек у C и A один и тот же: Hono, Postgres, Better Auth и pg-boss. Разница — в клиенте и протоколе: только в C продуманы синхронизация и миграции на устройствах. B проигрывает именно по моим критериям. RU-ячейка в нём становится вторым стеком, который нужно хостить самому, а самое слабое место — доставка статики в РФ — не закрыто.

Нагрузка варианты не различает. 800 тыс. сессий в месяц — это примерно 0,3 запроса в секунду в среднем, и 100k MAU выдержит один Postgres в любом варианте. Различаются варианты в другом: как они переживают отказ сети, переезд между регионами и изменение схемы данных.

Масштабу дан малый вес: его хватает всем трём вариантам. Доступности — наибольший: verify прямо называет полностью офлайн-PWA приоритетом №1 для РФ и предупреждает, что хостинг в РФ эту проблему не решает.

## 3. Пробелы во всех трёх вариантах

1. **Проектируют то, чего нет в продукте.** В спеке прямо сказано: «Глобального рейтинга нет: есть только друзья и компании». Тем не менее все три варианта строят глобальные и публичные доски, а в C есть ещё режим online-ranked с топ-100. При этом **компании** нигде не смоделированы, хотя это главный социальный формат M3: до 20 человек, общая цель недели, лента событий и реакции. Нет и **семейного режима** — до 6 локальных профилей на одном устройстве. Везде на клиенте только один пользователь.
2. **Origin и ячейки.** IndexedDB, OPFS, cookie и push-подписка привязаны к origin. Если у ячеек разные домены, гость, который установил глобальный PWA и при регистрации выбрал «Россия», потеряет локальный прогресс. Этого не решает ни один вариант, а A здесь противоречит сам себе: в одном месте «один origin, `connect-src 'self'`», в другом — «адрес API из `cells.json`».
3. **Телеметрия гостя.** Гость не привязан ни к одной ячейке. Куда отправляет ошибки гость из РФ? В A и C по умолчанию в Sentry, то есть иностранный SaaS получает IP. А это первичный сбор ПДн за рубежом. Маршрут телеметрии надо выбирать по зеркалу, с которого загружена статика, а не по аккаунту.
4. **Восстановление после потери сервера.** A и C обещают, что клиенты сами дозагрузят данные. Но уже подтверждённые события клиент повторно не отправляет, а новое устройство в C получает только снимок состояния и последние 50 сессий. Без `server_epoch` (сигнала «курсор сброшен, отправь всё заново») это обещание не работает.
5. **Режим двух устройств** (M4: телефон-камера сбоку, экран спереди) требует realtime-канала раньше, чем дуэли. Нужен он дома, где мобильный интернет может быть под белым списком. Ни один вариант этот режим не упоминает. Решение — WebRTC внутри локальной сети: прямые адреса без TURN, сигналинг через QR-код, без сервера.
6. **Push в РФ** ненадёжен во всех вариантах. Честнее всего запасные пути — `.ics` в A и напоминание при открытии приложения в C.

## 4. Вариант A: монолит

**Сильные стороны:**
- один образ, ячейка задаётся через `.env`;
- RU-стек расписан конкретно: Timeweb, Selectel или Yandex, GlitchTip внутри ячейки, бэкапы у другого провайдера той же страны;
- несколько версий симуляции через npm-алиасы;
- oasdiff в CI ловит ломающие изменения API;
- уйти от хостинга можно за часы.

**Слабые стороны:**
- **Курсор синхронизации** — глобальный `updated_seq` плюс «безопасный горизонт» 2 с. Это эвристика. Транзакция длиннее 2 с закоммитит строку с меньшим номером уже после горизонта, и клиент её пропустит. Запрос с перекрытием смягчает проблему, но не устраняет. Корректный вариант — курсор на пользователя, как в C, или горизонт по `pg_snapshot_xmin`.
- **LWW по `client_ts`** с окном в 30 дней работает без HLC, поэтому исход конфликта решают часы двух устройств.
- **`progress.plans.items jsonb` уходит на сервер.** Если в плане есть исключённые вариации («без упора на прямых руках», «только с колен»), это косвенные данные о здоровье. Именно о таком выводе предупреждает verify (C-184/20, C-21/23).
- **`GET /v1/analyses/file_sha256/{h}`** передаёт серверу хеши пользовательских треков. А спека ритма говорит, что в v1 сервер «не получает ничего, кроме анонимной телеметрии».
- **Старые клиенты.** Их запись получает 426. Правило «удалить операцию при `rejected`, оставить при 5xx» этот случай не покрывает: судьба outbox не определена.
- **Миграции Dexie не описаны вовсе.** Ничего не сказано и о том, что Safari через 7 дней без визитов стирает данные гостя.
- Обещание «перенос пользователя между ячейками — за минуты» игнорирует три вещи: VAPID-ключи у каждой ячейки свои, поэтому push-подписки придётся пересоздать; дружбы обрываются на границе ячеек; у клиента меняется origin.

## 5. Вариант B: Supabase

**Сильные стороны:**
- быстрый старт;
- Realtime Broadcast и Presence из коробки — лучшая основа для дуэлей и уведомлений «друг побил рекорд»;
- дисциплина «Supabase как дистрибутив Postgres»: SQL в git, `supabase-js` только в одном адаптере, свой домен, ночной дамп, репетиция выхода.

**Слабые стороны:**
- **Доставка в РФ не продумана.** Статика PWA лежит на GitHub Pages или Cloudflare. При троттлинге до 16 КБ на ресурс первая загрузка 13,5 МБ WASM и моделей не пройдёт, и офлайн-PWA просто не установится. Аудио для РФ продублировано, оболочка приложения — нет.
- **Если друзья в РФ, RU-ячейка с первого дня — это self-hosted Supabase примерно из 11 контейнеров.** Одному человеку придётся вести два режима эксплуатации: managed и self-hosted. Преимущество managed пропадает именно там, где доступность важнее всего. Работают ли кастомный OIDC и Send SMS Hook в self-hosted GoTrue — (н/п). С такими оговорками оценка выхода в 1–2 дня выглядит оптимистично.
- **Курсор `server_seq`** берётся из sequence и обновляется триггером на UPDATE. Проблема порядка коммитов та же, что у A, только здесь от неё нет никакой защиты. Это прямой баг: строки будут пропадать из pull.
- **Привязка к Supabase прямо в SQL:** `realtime.send()` внутри `finalize_session`, `storage.foldername`, Vault для связки pg_cron → pg_net. Для `auth.*` план выхода предлагает заглушки, но `realtime.*` и `storage.*` так не заменить, их придётся переписать.
- **`plan_state.week_template jsonb`** даёт ту же утечку, что у A, хотя заявлено, что сервер видит только уровень.
- **Доски `fp:*` и поиск по simhash для своих треков** противоречат спеке ритма.
- **Масштаб.** Realtime на Pro — 500 одновременных соединений (backend.md), сверх лимита — доплата (н/п). Анонимные пользователи раздувают MAU.
- **Миграции.** На устройстве описан только перенос из localStorage. Функции выкатываются двумя способами: `functions deploy` в облаке и rsync в `volumes` в RU-ячейке. Это путь к расхождению ячеек.

## 6. Вариант C: local-first

**Сильные стороны — как раз по моим критериям:**
- **Курсор на пользователя.** `user_seq` выдаётся через `update users … returning`. Это единственная из трёх корректная схема pull, и автор объясняет, почему глобальный номер ошибочен.
- **Слияние.** Гибридные логические часы (HLC), коммутативная свёртка в общем пакете `progress-core` на клиенте и сервере, компенсирующие события вместо правки истории.
- **Миграции на устройстве:**
  - проекции — кэш, который можно пересобрать;
  - события только добавляются, старые версии читаются через upcaster;
  - тесты прогоняются на дампах Dexie каждой выпущенной версии;
  - сервер принимает версии v и v−1;
  - экран «обновите приложение» по `minClientV` не трогает outbox.
- **Офлайн проработан глубже всех:**
  - один агент синхронизации на все вкладки (Web Locks);
  - `persist()` для хранилища;
  - сессия на 90 дней, а при истёкшем входе события не удаляются;
  - призраки для вызовов скачиваются заранее;
  - доски кэшируются с отметкой времени;
  - офлайн-билеты действуют 7 дней.
- **Переезд между ячейками** сводится к повторной отправке журнала. Регион можно выбрать не сейчас, а к M2.
- **План не синхронизируется**, поэтому утечки, как у A и B, нет.

**Слабые стороны:**
- **Противоречие с наградами.** В одном месте: «награды записываются в событие в момент игры и не пересчитываются». В другом: «сервер не доверяет итоговым суммам и пересчитывает всё сам». Выбрать нужно второе: сервер считает XP и самоцветы по `rules_v` из фактов сессии, а значение на клиенте — предварительное.
- **Не описано сжатие журнала.** `user_events` растёт на 2–3 ГБ в месяц. Партиции предусмотрены, но нет ни политики архивации холодных партиций, ни снимков на клиенте.
- **Правило «первая общая изменяемая сущность → переход на PowerSync» слишком грубое.** Компании из M3 формально его сразу запустят, хотя им нужен не движок синхронизации, а онлайн-команды и серверная проекция.
- **Рейтинг друзей.** Тай-брейк по доле выполненного плана требует, чтобы сервер знал размер плана, а план не синхронизируется. Нужно событие `plan_summary {sessionsPerWeek}` без подробностей.
- **Бэкап RU-ячейки** указан как «в B2 или Yandex S3». Для РФ подходит только российское хранилище: копия за рубежом — это хранение за рубежом.
- **Объём своего протокола** (~1,5 тыс. строк) оценён оптимистично. Симулятор синхронизации здесь обязателен, а не просто желателен.

## 7. Лучший гибрид

**Клиент и протокол берём из C, сервер и эксплуатацию — из A, а realtime строим без вендора, как в B.**

1. **Клиент (как в C).** Журнал событий в Dexie, курсор `user_seq`, HLC, пересобираемые проекции, upcaster'ы, агент синхронизации на Web Locks, `persist()`. Добавить в события `profileId` для семейного режима, а в ответ pull — `server_epoch` для восстановления после потери сервера.
2. **Сервер (как в A).**
   - Один образ: Hono, Postgres 17, Better Auth с закреплённой версией, pg-boss. Ячейка задаётся через `.env`.
   - RU-стек, бэкапы и GlitchTip — по A.
   - Токены попыток и пересимуляция с `sim_version` через npm-алиасы; ledger с уникальным ключом; oasdiff в CI.
   - **Награды считает сервер.**
3. **Доставка статики.**
   - С первого дня одна и та же статика лежит на двух зеркалах **под одним hostname**, а GeoDNS направляет на нужное. RU-зеркало — Yandex Object Storage или CDN Selectel, глобальное — R2 или VPS. Так IndexedDB гостя не зависит от выбора ячейки.
   - API ячеек — поддомены того же сайта (`ru.api.`, `eu.api.`), у каждой ячейки свой cookie, CORS с credentials.
   - Ошибки гостя уходят в GlitchTip того зеркала, с которого загружен PWA.
   - Если схема с GeoDNS не взлетит (сертификат на обоих зеркалах выпускается через DNS-01), берём разные домены и явный «перенос гостя» по коду или файлу.
4. **Убрать лишнее из продукта:**
   - никаких глобальных и публичных досок и никакого режима online-ranked: только друзья, компании, «Планка дня» и вызовы на общем seed;
   - свои треки в v1 сервер не видит, отпечаток передаётся в ссылке-вызове;
   - компании — это онлайн-команды и серверная проекция;
   - план не синхронизируется, на сервер уходит только `plan_summary`.
5. **Realtime по ступеням:** сначала SSE-«тычок», потом WS-комнаты в том же Node, затем Centrifugo с Valkey. Режим двух устройств — WebRTC в локальной сети с QR-сигналингом, без сервера. Supabase остаётся только как один из managed Postgres для глобальной ячейки, без его Auth, RLS и Edge Functions.
6. **Масштаб к 100k MAU:**
   - партиции `user_events` по месяцам и снимки `user_state(through_seq)`;
   - холодные партиции старше 12 месяцев переносятся в S3;
   - Valkey подключаем, только когда p95 превысит 50 мс;
   - PITR или WAL-G — с Ф1.

## 8. Что проверить до решения

- Не нужен ли для RU-зеркала российский TLS-сертификат. В адресе одного из источников verify упоминается запрет «зарубежных сертификатов» (н/п). Это касается связки Caddy и Let's Encrypt в RU-ячейке у A и C.
- Как схема GeoDNS с одним hostname работает под белыми списками. Если зеркала нет в перечне, остаётся только офлайн.
- Не попадает ли вход по номеру телефона для пользователей из Узбекистана под локализацию «данных абонентов операторов связи» по ЗРУ-1125. До проверки не включать телефонный вход для UZ в global-ячейке.
